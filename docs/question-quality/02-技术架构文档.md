# 拾词技术架构文档 · 八选一释义去重

沿用现有 Vue 3、TypeScript、Vite 和静态词库。用同一个出题入口供初筛、复筛、导出与构建验题调用，沿用 IndexedDB、JSON 备份、Service Worker 和 GitHub Pages 发布流程。

## 一、复用现有模块

| 模块 | 技术栈和改动 |
| --- | --- |
| 词源与数据 | 三套经过固定来源校验的 JSON 词包，保留词库 ID、内容版本、词条 ID 与展示释义。复用雅思词包已有的其他义项、词形信息。人工审核规则按词库或题目记录来源、冲突词和理由。 |
| 出题与校验 | TypeScript 的 `src/domain/questions.ts`。沿用原表取项和已审近义词组，增加同题八项两两比较。显示给用户的选项文字取自原表；规范化文本供内部比较。 |
| 审计 | Node.js 构建脚本。复用 `check:questions`、`check:cet-questions`、`check:ielts-questions` 和 BIC-22 抽样方式。统一输出词库、目标词、重复项、规则与复核结论。 |
| 存档与备份 | `screeningStorage.ts`、`review.ts`、`studyTools.ts`。将不同题目版本纳入校验，沿用词库隔离、修订号检查、事务和旧格式恢复。 |
| 测试与发布 | Vitest、fake-indexeddb、Playwright。沿用 GitHub Actions 构建与 Pages 发布，验收浏览器和主屏幕应用在联网、离线和版本切换时的行为。 |

## 二、出题规则

1. 为每个候选保留来源词 ID、原有释义和比较用的独立义项。比较时统一全半角、常见标点与分隔符，并保留括号内解释的边界。按原词库保留专有词、英文异体和多义词的区别。
2. 把目标词的核心义放入已选项。评估候选时先检查它是否能解释目标词，再与已选干扰项比较。采用文字相同、义项交集、已确认的词形关系和人工确认的近义冲突。把语义范围较宽、需要上下文的命中列入审查。
3. 原类别中选项不足时，从同一词库的更大候选范围补选，继续应用同样的排除规则。按稳定顺序选取来源词，保留现有题序和选项的随机化入口。若仍不足七项，在构建报告中定位该题供人工解决。
4. 生成后对每道题的 **28 对**选项做独立校验。原表来源、选项数、正确项、规则命中都可追溯。若扩展正则会误伤固定搭配，用逐题复核后的明确规则处理，并保存覆盖案例。

## 三、题目版本和存档兼容

现行题目版本为 `source-meanings-v2`。题目签名包含选项 ID 和文字，替换一项即可改变整套题的签名。初筛存档、复筛轮次及 JSON 恢复都依赖这套校验，因此要把兼容逻辑作为出题规则的一部分验收。

| 场景 | 方案 |
| --- | --- |
| 验证历史答案 | 保留现行 v2 题库的确定性生成或可复现快照，按词库、词条 ID、题目版本校验历史答案。保留旧选项 ID、选项文字和当时的对错。旧干扰项已下线时，历史记录继续使用旧版选项。 |
| 同一轮混合旧题与新题 | 提升题目规则版本，新作答标注实际版本。存档校验允许经验证的历史记录与新作答共存，沿用任务 ID、修订号和已答词集合。未完成复筛按原轮次的词条 ID 继续。 |
| JSON 备份和浏览器升级 | 复用原词库标识与 IndexedDB 键。涵盖最早的考研备份和当前三库备份。读取或写入发生冲突时保留原存档。验证旧页面与新页面同时打开、刷新中断和导入失败。 |
| 回退 | 准备能读回 v2 和新版本混合档案的回退构建，以旧出题规则恢复可用性。先在同一测试地址写入新答案，再回退验证这些答案、复筛轮次和导出内容。 |

当前历史迁移有一处会在旧选项找不到时以另一个干扰项代填。本任务需要验证并改用历史选项校验路径，防止更换选项时误写用户曾选的内容。[当前存档校验代码](../../src/domain/screeningStorage.ts)

## 四、验收入口

沿用 `npm test`、`npm run build` 和 `npm run test:e2e`。用隔离浏览器配置生成旧版测试数据，在同一测试地址执行升级、刷新、断网续筛和回退。发布后检查首页、词包和 Service Worker，再用测试记录完成一道修复题。生产资源继续使用当前站点地址和本地存储。
